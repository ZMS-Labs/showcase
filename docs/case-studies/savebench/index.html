Decision / September 18, 2026

The success condition
needed to fit the question.

An AI model bought milestones by feeding machines by hand and never built a conveyor belt. At first I called that a flaw. Then I decided SaveBench measures factory design, rather than whether a model chooses to automate.

The revised test counts delivery to a declared depot after the factory has been left untouched for a set period. It asks whether the designed system keeps meeting a production quota.

Observed outcome / September 22–23, 2026

The new test
had not recorded a pass.

The first and fourth sessions were recorded as inconclusive because the factory had not been left untouched long enough. Their instructions omitted the hands-off rule, and the required 600 game seconds was an unintended default. A next session stated the rule and requested 60 seconds; it had no recorded result as of 03:52 UTC on September 23.

This is a test-design decision, not a performance improvement or adoption claim. No new game trial was run for this preview.

A real experiment: test the instrument first.

These two trials ran in the game on 9 September 2026, and the prototype below played no part in them. An AI agent designed the factory they measured; SaveBench calls an AI taking part a contestant. The agent started with a fresh context and was given only the challenge and the tools every contestant gets, and the record shows its design used only those. It chose copper and limestone deposits on the map and placed 34 buildings, 15 belts and 7 power lines. Nobody changed its design afterward.

The instrument is the measuring tool: an adapter that writes a factory design into a game save file, and an evaluator that records what the running game delivers. Each trial starts with controls, which are tests with a known answer. The known-flow control is a test factory that should deliver both products; the disconnected control is the same factory with its connection removed, so it should deliver nothing.

Step 1 of 5

The known-flow control reports zero.

This control should deliver both products. Instead, it records zero copper ingots and zero concrete in each of two 61-second windows, timed by the game’s own clock.

The trial stops as INCONCLUSIVE before the contestant’s factory is measured. The missing measurements are not scored as zero production.

Repair the measuring tool, then check both controls.

The trial record traces the fault to the adapter. It filled in a storage filter that the game leaves empty in its own saves, so the control’s materials reached the belts but the depot counted none. The fix was to write the filter the way the game does.

In the new trial, the known-flow control delivers both materials, and the disconnected control delivers nothing, as it should. Together they show the tool can see a delivery and can see when there isn’t one.

Measure the same design with the repaired tool.

The factory design and the task are identical in both trials, byte for byte, and both trials name the same challenge and design revision.

What changed is the measuring tool: the adapter, the contestant tools’ code and the evaluator’s recorded version are all different, so the contestant’s save file was rebuilt and its bytes differ. This is the same design measured again with a repaired tool, not a rerun of identical files.

Judge every window against both targets.

The contestant’s factory delivers copper ingots and concrete. The rule, fixed in advance, requires at least 20 copper ingots a minute and 15 concrete a minute in every measuring window. Measuring begins after 180 game seconds of warmup.

Copper misses in the first window. Both products meet their targets in the second. Concrete misses in the third. Later copper production does not cancel an earlier miss.

Retain the miss instead of moving the target.

The repaired trial is scored FAIL against the same per-window targets. The earlier INCONCLUSIVE attempt stays on the record as its own result. The FAIL is useful because it’s specific: the factory produced both materials, just not enough of each in every required window.

The two misses have different causes. When measuring began, no copper had reached the depot yet; the record says that fits copper still traveling the long belt route, but it doesn’t prove it. For concrete, the design used one concrete machine. At normal speed one machine makes 15 a minute, the target itself, and this challenge had no way to speed a machine up. The third window’s 121 game seconds needed 30.25 concrete to meet the target, and it delivered 30.

The next day, the same 180-second default warmup left three reference factories, built to pass their own challenges in SaveBench’s library, short in their first window. Challenges in that library now set their own warmup. This FAIL was not rescored.

Both results stay as recorded: no verdict from the first trial and a FAIL from the second, with no combined score and no loosened target.

What made the failure useful.

Three rules made this failure worth keeping. Check the instrument with a test whose answer is already known before trusting what it reports. Keep the question fixed, so the design and targets stay the same through a repair. Keep every window, so a good stretch later can’t cancel an earlier miss.

What happened next.

On 13 September, factories designed by Claude Opus 4.7 and GPT-5.5 (both as configured) passed a harder challenge in the game: 120 copper ingots and 60 concrete a minute in every window, with faster belts allowed. Both also had FAILs in those comparisons, which aren’t a ranking.

Then the work moved to a campaign in a persistent world, judged by the game’s own milestones. On 18 September I decided the test would be a production quota the factory has to keep meeting while nobody touches it, an approach from the Factorio Learning Environment research benchmark. No quota session has passed in the records through 23 September, and the contestant, Cursor’s Auto setting, wasn’t told the hands-off rule until the latest one, which has no result yet. The records don’t show which model Cursor’s Auto setting used.

Dates are UTC, as in the run records. The raw record (JSON) lists each result with its limits.

The prototype.

It puts the factory map beside the challenge’s conditions, the revision you’re looking at and an activity feed. In its sample data, A and B are two contestants and the number counts revisions: A1 is A’s first design, A2 its second, and B1 is B’s first. Earlier builds of this interface started real comparisons between AI models on 12 and 13 September, including the passes under What happened next.

Give a factory a concrete job.

A challenge defines outputs, resources, a region, permitted equipment and measurement conditions. Contestants respond with recipes, machine placements, transport connections and revisions. The game decides whether that arrangement works.

I want to see the design process as well as the result: what a contestant proposes, changes and keeps. What the prototype shows is each contestant’s public plan and its revisions, not a model’s private reasoning.

Compare more than an output rate.

I want the comparison to make different approaches visible while keeping measurements separate from judgments about an interesting design.

Space and connections

A compact layout and a sprawling one may meet the same target. Recipes and transport choices change how they get there.

Conditions and revisions

Set allowed choices and targets before the run. Keep earlier attempts so a later result has a history.

What went into this work.

Direction
I want AI models to design factories and the game itself to judge them. A factory that only works on paper isn’t nearly as interesting to me.
What I did
I decide what each project is for and check what comes back. The 18 September call on what SaveBench measures was mine.
What the AI did
AI tools write the code. For SaveBench that means its own code: the prototype’s interface, the adapter that writes designs into save files through an open-source save library, the evaluator and the tests. They also helped prepare this page, and AI contestants designed the factories judged here.

That save library is Satisfactory Agent Tools by petehunt, itself a fork of GreyHak’s sat_sav_parse. The adapter uses a fixed version of it, and both projects are licensed GPL-3.0.

The 9 September run was an early test. The AI agent coordinating the work wrote the designer’s instructions for that run instead of using a frozen set, so the result stands on its own and isn’t compared with any other run. The designing agent isn’t named, because the only record of its model is private session data. Later model names carry their basis, as the runtime reported or as configured, and no run’s model was independently confirmed.

The prototype views and the recording show the prototype’s own screens and controls running on made-up sample data, with no game, AI model or server behind them. Its rectangles and routes are sketches that don’t show whether a layout would fit or connect in the game. No independent test of the interface itself was finished.

The walkthrough’s diagrams and tables were drawn for this page from the trial records. No game screenshot, map tile, save file, application source or private operational detail is published here. The 9 September result covers one design on one challenge.
