Poiesis · A shared service for generated files

Which file came back, and how long should it stay?

I wanted apps to share one service for generating text and images without losing track of what came back or keeping it forever. Poiesis is that service, and it’s still an experiment. This case study looks at two rules: you get back exactly the file that was made, and nothing stays available forever.

In plain terms.

Eight tests passed with no AI model running: a returned file matches its fingerprint (a code computed from its exact bytes), files expire after 24 hours whether or not anyone collects them, and stored prompts become unreadable once a job finishes.

Follow the five steps.

The eight tests run the service’s own code for jobs, images, requests and stored prompts. Each step below covers one or more of them and says what they showed.

Return the image, then fetch it.

The image engine’s code runs, but its request goes to a stand-in that answers with a small PNG image made for the test. The job finishes with exactly those bytes. A second test fetches the image back through the service and checks that it carries an expiry time.

The image came back unchanged

The image handling ran on a real PNG file, and the file fetched back matched it byte for byte.

Fingerprint the returned text.

A stand-in text generator sends “Hel” and then “lo” as the text streams in, and returns “Hello”. The service records one text file, marks the job complete and stores the exact bytes with their fingerprint.

The pieces and the final file agree

The test checks both pieces, the final five bytes, the fingerprint and the text/plain file type.

Refuse the file after its deadline.

The test fetches its sample file once, then moves the test clock to 24 hours and one second after the file was made. The next request for the file is refused. A cleanup call then reports one file deleted.

409A refusal after the deadline

The request is refused before anything is deleted, and the test checks both. In the service’s code, a file that never existed gets this same refusal on purpose, because after the deadline an app has no reason to tell the two apart.

Delete files nobody collected.

A second sample file is never fetched. At 25 hours, a cleanup call deletes it and leaves the job with no files.

Not collecting a file doesn’t keep it longer

An app that wants a file has to collect it within 24 hours.

Keep the prompt locked, with its key apart.

Three tests check the stored prompt. It waits in the work queue locked, its key is deleted when the job finishes, and it can’t be unlocked under a different job’s ID. The next section explains why it’s built this way.

Recover work without keeping its prompt indefinitely.

A worker, the part of the service that runs a job, may fail after accepting it. A second worker needs enough information to continue, which makes custody of the prompt (who holds it, and for how long) a real design problem: making work recoverable also creates something that could be kept too long.

The lock is also tied to the job’s ID. A test tries to open the prompt under another job’s ID, and it fails.

Decide how long each thing is kept.

Choice
The prompt and the returned files end in different ways. When a job finishes, the prompt’s key is deleted, so the stored prompt becomes unreadable. Returned files expire 24 hours after they’re made, and a cleanup call deletes them whether or not anyone collected them.
Tradeoff
A set lifetime can make useful content unavailable. Recovery and delivery must fit within that limit; retrying forever would defeat it.

What the tests show, and what they leave open.

What is real here

Eight of the service’s own tests passed on 19 September 2026 against source revision de39639. Zero failures, zero skips and zero attempted external connections.

They ran on Python 3.11 with made-up data, storage held in memory, a clock the tests control and stand-ins for the text and image generators. The steps come from different tests, not one recorded job.

The tests don’t show:

  • Real generation, or how good generated images or text would be.
  • Storage that lasts beyond a test run.
  • Cleanup that runs on a schedule by itself. Every deletion here came from a call the test made.
  • Whether every other copy of a key, such as one in a backup, is erased.
  • A second worker picking up a job after the first one fails.
  • Whether the service stays available in real use.
  • Whether a 24-hour limit fits any wider policy on keeping content.

What a fingerprint shows

The fingerprint shows these are the exact bytes that came back. It doesn’t show who made the file or who owns it, whether its content is true, or how good it is.

You can check the “Hello” fingerprint yourself: printf 'Hello' | sha256sum prints the same 64 characters.
