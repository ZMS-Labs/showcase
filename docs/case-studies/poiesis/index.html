Poiesis · Shared generation

Every file gets a receipt and an expiry date.

Several of my apps share one service, Poiesis, for generating text and images. Each app needs proof of exactly what came back, a clear date when the file goes away, and prompts that don't linger once the job is done.

How it works

Follow the five steps.

The eight tests run the service's own code for jobs, images, requests and stored prompts. Each step below covers one or more of them and says what they showed. The steps come from different tests, not one recorded job.

Return the image, then fetch it.

The image engine's code runs, but its request goes to a stand-in that answers with a small PNG image made for the test. The job finishes with exactly those bytes. A second test fetches the image back through the service and checks that it carries an expiry time.

The image came back unchanged.

The image handling ran on a real PNG file, and the file fetched back matched it byte for byte.

Fingerprint the returned text.

A stand-in text generator sends "Hel" and then "lo" as the text streams in, and returns "Hello". The service records one text file, marks the job complete and stores the exact bytes with their fingerprint.

The pieces and the final file agree.

The test checks both pieces, the final five bytes, the fingerprint and the text/plain file type.

Refuse the file after its deadline.

The test fetches its sample file once, then moves the test clock to 24 hours and one second after the file was made. The next request for the file is refused. A cleanup call then reports one file deleted.

A refusal after the deadline.

The request is refused before anything is deleted, and the test checks both. In the service's code, a file that never existed gets this same refusal on purpose, because after the deadline an app has no reason to tell the two apart. That last point comes from reading the source, not from the tests.

Delete files nobody collected.

A second sample file is never fetched. At 25 hours, a cleanup call deletes it and leaves the job with no files.

Not collecting a file doesn't keep it longer.

An app that wants a file has to collect it within 24 hours.

Keep the prompt locked, with its key apart.

Three tests check the stored prompt. It waits in the work queue locked, its key is deleted when the job finishes, and it can't be unlocked under a different job's ID. The next section explains why it's built this way.

Stored prompts

Recover the work without keeping the prompt forever.

A worker, the part of the service that runs a job, may fail after accepting it. A second worker needs enough information to carry on. That makes custody of the prompt, meaning who holds it and for how long, a real design problem: making work recoverable also creates something that could be kept too long.

So the locked prompt and its key live in different places. The lock is also tied to the job's ID: a test tries to open the prompt under another job's ID, and it fails.

Holds the locked prompt

Work queue

Holds the prompt, encrypted, along with the job's details. A test looks through everything in the queue and finds no readable copy of the prompt.

Holds the key

Job record

Holds the key, apart from the prompt. When the job finishes, the key is deleted. A test keeps a copy of the locked prompt, standing in for a backup, and shows it can no longer be opened.

Where the prompt and its key sit in the tests.

Design tradeoff

Decide how long each thing is kept.

The prompt and the returned files end in different ways. When a job finishes, the prompt's key is deleted, so the stored prompt becomes unreadable. Returned files expire 24 hours after they're made, and a cleanup call deletes them whether or not anyone collected them. Steps 3, 4 and 5 above show both.

The cost: a set lifetime can make useful content unavailable. Recovery and delivery have to fit inside that limit; retrying forever would defeat it.

How they ran

The tests ran on Python 3.11 with made-up data, storage held in memory, a clock the tests control and stand-ins for the text and image generators. No AI model, graphics processor or live generation service was called.

Beyond the two gaps in the record above, the tests don't show:

  • Real generation, or how good generated images or text would be.
  • Storage that lasts beyond a test run.
  • A second worker picking up a job after the first one fails.
  • Whether the service stays available in real use.
  • Whether a 24-hour limit fits any wider policy on keeping content.

What a fingerprint shows

The fingerprint identifies the bytes that came back. Authorship, rights, accuracy and quality need separate evidence.

You can check the "Hello" fingerprint yourself: printf 'Hello' | sha256sum prints the same 64 characters.
