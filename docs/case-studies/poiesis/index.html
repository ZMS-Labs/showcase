Poiesis · Shared generation infrastructure

Keep a receipt.
Set an expiry.

I wanted applications to share a generation service without losing track of what came back or keeping content indefinitely. Poiesis is that experimental service. My focus here is its surrounding service design: identifying returned bytes, delivering them and setting explicit content lifetimes.

Follow the evidence boundary.

The eight checks exercise existing executors, an image adapter, API handlers and prompt-custody code. Transports are stubbed and stores are in memory. Each step states what its related tests establish.

01 · Return and retrieve the supplied image.

The existing image adapter runs through a controlled transport that supplies a small, valid PNG fixture. The executor completes with that exact byte payload. A related test fetches it through the API and checks that an expiry is attached.

Adapter and retrieval paths exercised

The adapter handles a real encoded image, but the backend is a stub. This does not assess a model’s ability to generate a useful image.

02 · Fingerprint the returned text.

A separate stubbed text adapter emits “Hel” and “lo” to a stream sink and returns “Hello”. The executor records one text artifact, marks completion, and stores the exact bytes with their SHA-256 digest.

Fragments and final artifact agree

The test asserts both fragments, the final five bytes, the digest and the text/plain media type. It covers the executor’s handling of a controlled adapter, not a live text-generation backend.

03 · Reject access after the deadline.

The retention test first retrieves its fixture, then advances the controlled clock to 24 hours and one second after creation. A later fetch is rejected as expired. Calling the purge method reports one removal.

409Expired artifact

The observed API result is distinct from physical cleanup. The test invokes cleanup explicitly; it does not observe a production scheduler.

04 · Do not retain it forever because nobody collected it.

A second fixture is never fetched. At 25 hours, explicit purging removes it and leaves the generation’s artifact list empty.

Non-delivery does not extend retention

The consumer must collect useful output within the service’s window. The demonstrated rule favors a bounded lifetime over indefinite retry-driven retention.

05 · Give the prompt its own custody boundary.

The queue-custody tests inspect encrypted prompt storage, removal of the recorded key after settlement, and rejection when the sealed prompt is used with a different generation ID.

Separate mechanisms for input and output

Prompt keys are cleared on settlement in these fixtures. Returned artifacts have a timed access window. In-memory assertions establish this behavior, not physical erasure across backups or running infrastructure.

Recover work without keeping its prompt indefinitely.

A worker may fail after accepting a job. A separate worker needs enough information to continue, which makes content custody a real design problem: making work recoverable also creates something that could be retained.

Encryption also binds the prompt to its generation ID. The focused test rejects an attempt to use that sealed prompt under another ID.

Specify what ends custody.

Choice
Use distinct mechanisms for prompt custody and returned artifacts: settlement-driven key removal for the former, expiry plus cleanup for the latter.
Tradeoff
A bounded lifetime can make useful content unavailable. Recovery and delivery must fit within that limit; retrying forever would defeat the boundary.
Evidence
The checks exercise the selected transitions with synthetic fixtures. Physical backup separation, comprehensive deletion and deployed operations require different evidence.

A shared service with explicit boundaries.

Product and engineering direction
I direct the service design with AI assistance: how applications request work, how execution is recorded, and when custody of content ends.

Concrete checks, with a bounded conclusion.

Eight existing tests passed on 19 September 2026 against source revision de39639. Zero failures, zero skips and zero attempted external connections. The checks use Python 3.11, in-memory stores, a controlled clock and stubbed adapter transports.

What was exercised

Image handling and retrieval, a streamed text result and its fingerprint, expired access and explicit cleanup, plus three prompt-custody assertions.

What a hash establishes

The fingerprint identifies these bytes. It does not establish originality, ownership, factual truth, model quality or signed external provenance.

What remains outside this check

Live generation, durable-store integration, autonomous cleanup timing, backup erasure, production availability and broader retention-policy alignment.

How to read the diagrams

They explain separate fixtures from the test selection. They are not a product interface, a deployment map or a captured customer workflow.
