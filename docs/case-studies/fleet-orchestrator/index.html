Fleet Orchestrator · Keeping track of AI agents

Each agent gets its own look and its own record.

I want to keep track of several AI coding agents without losing their work between sessions. I often have a few running at once, each in its own window. Fleet Orchestrator is the workspace I’m designing to keep each agent’s identity, conversation, tasks and reviews in one place, so I can see who is doing what, what changed, and where I need to step in.

In plain terms.

The design gives each agent a recognizable icon and a running record on one screen, with a clear point where I step in before work moves on. This page shows the design of the agent icons and that main screen, filled with made-up agents, plus one working piece: a review gate that three tests show holding work back while a serious problem is open.

How a glyph shows who an agent is and what it is doing.

Each agent gets a glyph: an icon that stays recognizable while its work changes. The role sets the shape, and a ring around it shows what the agent is doing. The cockpit, the screen for following and directing the agents, shows those glyphs on its home screen, here in Stratus, the project’s own dark theme.

Role has a visual vocabulary

An implementer carries stacked blocks; a reviewer, a check panel; a writer, quill lines; a runtime bridge, a link bridge. Shape and motif identify the role. Each agent’s color and facets come out the same every time, which helps tell agents apart; color never marks the role.

Activity changes the ring

Running, review, handoff and blocked each get a different ring. An agent’s look comes from its name, its role, its lineage (the family of copies it belongs to) and its clone number (which copy it is), never from its state or the tool running it, so changing either leaves the inside of the glyph the same. Text labels carry the meaning alongside shape and color.

Detail grows with size

At 24 pixels a glyph keeps its silhouette and state ring. Larger sizes add the motif, facets and a badge for the tool running the agent. From 96 pixels a clone also shows as many tally marks as its clone number; clones in one lineage share a palette, and each turns 15 degrees further than the one before.

Keep the work coherent as sessions come and go.

Each agent has its own identity and its own record of work. A session is one run of that agent, and the goal is for the record to outlast it, so the work can be read somewhere other than a terminal window.

The home screen groups agents that work together. One kind of group is a crew: every agent assigned to the same project. The screen also lists the work that needs me. Say a crew has three agents: an implementer is at work, a reviewer is waiting on a decision, and a third agent is blocked. I wanted a view that makes those differences obvious at a glance, then lets me open the right conversation, the commands that ran, the files that changed and the review record before I step in. Fleet Orchestrator is the next problem along from Epistemic Skills, which grew out of wanting agents to check whether their changes worked.

The Surface Bridge connects decisions to execution.

The Surface Bridge is the part that takes a decision about what an agent should do next, turns it into commands for whichever AI tool is running that agent, and reports back how it went. Keeping the deciding apart from the running is what should let an agent outlast any one session. A central service, called the control plane, holds the agent and task record.

When the control plane wants something run, the bridge hands the request to the chosen runtime (the tool that actually runs the agent) as a process, a session or an API call. Each runtime has its own adapter for that translation, and the bridge sends back whatever progress and results that adapter can report. From the cockpit, commands and conversation turns (single messages to an agent) reach the control plane through a gateway, its entry point for requests.

Identity lives in the control plane

The goal for continuity is a recorded history and a summary of context, not a perfect transfer of a model’s internal state.

A clear line between deciding and running

The cockpit sends commands through the gateway and the control plane. The bridge handles the mechanics of each runtime; the control plane stays the one agreed record for the product.

Design notes (JSON)

A handoff is not a completion claim.

When an agent hands work back, I want to know what it actually finished and what it didn’t. In Fleet Orchestrator a reviewer looks at the work and can record a finding: a problem serious enough that the work should not move on. The review gate answers one question: is this work eligible to proceed? Two ideas run through it. An approval with no reason, reference or finding attached is refused, and routing a problem back to someone does not count as fixing it. The five steps below retrace what the project’s tests check, starting from a sample finding that says a required input check is missing. Across them the gate reads Blocked, Still blocked, Eligible, Eligible, then Blocked again.

Step 1 of 5

An open finding blocks the gate.

The reviewer records a high-severity finding with a summary and references to its evidence. The gate reports the finding as a blocker.

Routing the finding back keeps it open.

The finding is routed back to be fixed. A routing event is recorded, the finding stays open and the gate stays blocked. Keeping the finding open when the route is recorded lets the history show that a fix was asked for, and why the work is still held back.

A recorded fix removes this blocker.

The test marks the finding as fixed and checks three things: the new status, a timestamp for the fix, and an event recording the change. With no open finding left, the gate lets the work proceed. Marking a finding fixed only updates the record.

A verification waiting on a person leaves the gate allowed.

The next check records the verification as ready_for_operator, meaning it is waiting on a person to decide. The gate keeps allowing the work and returns that status next to its answer. Keeping the answer and the reason as separate fields lets whoever reads the result tell an open problem, work waiting on a decision and a failed check apart.

Failed verification blocks the gate again.

The underlying test also records a passed verification before changing it to failed. The gate then blocks again and reports the failed status. An earlier allowed response cannot stand in for a later check.

What these tests show and leave open

Three choices behind the gate.

Two of them show up in the steps above: routing a finding is recorded while the finding stays open, and the gate returns its reasons next to its answer. The third keeps each finding tied to its own task.

Bind a finding to its task.

Choice
Before changing a finding’s status, check that the finding belongs to the task named in the request.
Effect
An update sent through another task’s address is refused and leaves the finding untouched. The same update sent through the finding’s own task succeeds, which shows the update itself works when the task matches.
Boundary
This checks the link between a finding and its task in sample data. It does not test a real login.

What ran, and what it leaves open.

What is real here

Three tests already in the project passed on 19 September 2026, with zero failures and zero skips.

They ran the project’s real request-handling code against sample records kept in memory, with a launcher that starts no agents. The application code and the full test record are private; the public summary lists the checks shown on this page and the revision they ran against.

  • A review request sets up one reviewer and an inbox for it. A bare approval with no reason, reference or finding is refused, and an open high-severity finding blocks the gate.
  • Reading the inbox a second time doesn’t log the same message as received twice. Routing leaves the finding open, recorded status changes move the gate, and a failed verification blocks it again.
  • Updating a finding through another task’s address is refused as not found and leaves the finding unchanged, while the same update through its own task succeeds.

What remains unproved

The glyph and cockpit images come from the project’s own components, captured with its local setup and a system font. They don’t show a production build or full accessibility. The Surface Bridge map comes from reading the source, not from watching it run, and an adapter written for a runtime doesn’t mean that runtime is available or works as well as the others. Nothing on this page is a recording of the product in use.

The tests don’t show a real agent at work, a real database, data surviving a restart, a task finishing outside the test, or anything deployed. The rule against bare approvals checks that an approval comes with a reference, a sufficient reason or an existing finding; it can’t judge whether that evidence is true or any good. Only open high or critical findings block the gate. A separate, optional check for what the project calls candidate findings is off by default and was not run.
