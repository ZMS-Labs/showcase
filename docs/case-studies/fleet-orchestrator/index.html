Keep the work coherent as sessions come and go.

The organizing unit is an agent with an identity and a work record. A runtime session is one way that agent executes work. The product direction connects those pieces without making a terminal window the only place the work can be understood.

Consider a crew with an implementer at work, a reviewer awaiting a decision and another agent blocked. The cockpit is designed to make those differences visible, then let the operator move into the relevant conversation, commands, changed files and review record before intervening.

This describes the intended operator journey. The component specimens and focused test results below establish narrower parts of it; they do not demonstrate a newly executed end-to-end crew session.

Role has a visual vocabulary

An implementer carries assembled blocks; a reviewer, an inspection panel; a writer, quill lines; a runtime bridge, linked nodes. Shape and motif identify the role. The seeded palette and facets help distinguish an identity.

Activity changes the surround

Running, review, handoff and blocked states have different rings. State and runtime do not enter the identity seed, so changing either leaves the interior identity stable. Text labels carry the meaning alongside geometry and color.

Detail responds to scale

The smallest glyph keeps silhouette and state ring. Larger sizes reveal motif, facets and a runtime badge. Full-size lineage specimens add clone tallies; related clones share a palette and use rotational variation.

The Surface Bridge connects decisions to execution.

A central service, called the control plane, holds the agent and task record. The Surface Bridge translates its requests into runtime-specific processes, sessions or API calls, then returns the progress and results that adapter supports.

Identity lives in the control plane

Changing an execution session should not erase the agent’s identity or recorded task context. The continuity goal is recorded history and summarized context, not perfect transfer of a model’s internal state.

An explicit execution boundary

The cockpit sends commands through the gateway and control plane. The bridge handles runtime mechanics; it is not the canonical authority for the whole product.

Runtime support varies by adapter

An implemented adapter or a reachable endpoint does not establish successful work. Runtime support varies, and this case study makes no claim that every integration is live or equivalent.

A handoff is not a completion claim.

One concrete component illustrates the coordination problem. Start with a synthetic high-severity finding: a required input check is missing. These diagrams explain assertions from existing source tests; the controls do not run the application.

Step 1 of 5

An open finding blocks eligibility.

The reviewer records a high-severity finding with a summary and evidence references. The gate reports the finding as a blocker.

This is a state check. It does not establish that the synthetic finding describes a real defect.

Routing a fix does not resolve it.

The finding is routed back for attention. A routing event is recorded, but the finding stays open and the gate stays blocked.

The distinction matters: “someone should address this” is not evidence that it has been addressed.

A recorded fix removes this blocker.

The test changes the finding’s status to fixed. It checks the updated state, a resolution timestamp and a status-change event. The gate now permits eligibility with zero finding blockers.

The handler records the finding as fixed; it does not independently check the code fix.

Ready for the operator can still be allowed.

The next assertion records verification as ready for the operator. The gate continues to allow eligibility while returning that exact status.

A consumer must read both fields. Treating allowed=true as “verification passed” would erase a distinction the response preserves.

Failed verification blocks the gate again.

The underlying test also records a passed verification before changing it to failed. The gate then blocks again and reports the failed status.

Eligibility is recalculated from the current records. An earlier allowed response cannot stand in for a later check.

Eligibility is not completion. The illustrations summarize related isolated tests, not one captured live session. The five steps focus on the gate assertions within that test set.

A route is an action, not a resolution.

Choice
Record the routing event without clearing the finding.
Effect
The review history can show that a fix was requested while preserving the reason work remains blocked.
Boundary
A recorded request does not prove an agent received or performed the fix.

Return the reason alongside the result.

Choice
Keep gate eligibility, finding blockers and verification status separate.
Effect
An operator or downstream consumer can distinguish an open issue, readiness for a decision and a failed verification.
Boundary
The consumer still has to interpret those fields correctly. An allowed gate is not a general claim of correctness.

Bind a finding to its task.

Choice
Check that the loaded finding belongs to the task named in the request before changing its status.
Effect
The wrong task URL is rejected and leaves the finding untouched. A matching-task update succeeds as a positive control.
Boundary
This verifies resource binding in the fixture, not production authentication.

A bounded, checkable result.

Three existing tests passed on 19 September 2026. Zero failures. Zero skips.

The tests exercise real HTTP handlers with synthetic records, an in-memory store and a launcher that starts no agents. The public summary reports selected assertions; application source and the full private verification receipt are not included.

  • Review loop: a handoff creates a review request; a bare approval with no rationale, references or finding is rejected; an open high-severity finding blocks the gate.
  • Gate and event sequence: repeated mailbox reads add no duplicate receipt event; routing preserves the open finding; recorded status changes affect the gate; failed verification blocks it again.
  • Task binding: a cross-task finding update returns 404 without changing the finding, while the matching-task update succeeds.

What remains unproved

These tests do not establish live agent behavior, production database persistence, restart recovery, production authentication, external task completion or deployment readiness.

The bare-approval guard checks for a reference, sufficient rationale or an existing finding. It cannot establish the truth or quality of that evidence. The finding rule concerns open high/critical findings; a separate optional candidate-finding gate was not exercised.

The review-gate diagrams are selectable explanations of checked assertions. The architecture map is source-based explanation. The separate glyph and cockpit captures use existing components with synthetic inputs; none is a production activity recording.
