Whose experience is this?

Imagine you are running a short scene with two characters, Guide and Archivist. Each character keeps its memories in its own collection, apart from yours. The scene was made up for this page to explain what the tests check, and the diagrams were drawn for it as well, so clicking through them does not run Enaction.

Step 1 of 5

Choose who is speaking.

You pick Guide and type, “I will bring the blue folder.” That choice says who is talking in this scene, and your own profile stays as it was.

Enaction checks the pick before using it. It refuses your own identity as a character, and it refuses a character who is not in the scene.

Keep the character fixed once the turn is prepared.

When a turn is prepared, Enaction saves the chosen character along with the line. Each request carries an ID so Enaction can recognize a retry. If a retry with the same ID names Archivist instead, Enaction treats it as a conflict and keeps Guide.

While a turn is being prepared or is waiting to be accepted, the workspace also locks the role controls and says why.

Give the memory to the character who spoke.

After you accept a manual turn, where the character’s reply is entered by hand and no AI model runs, Enaction files the memories it produces under the character saved with that turn. The test uses two characters and runs once with each one chosen. Every memory from the turn lands with the character who was speaking, and none land anywhere else.

New memories still wait for review. Putting one in the right place does not approve it, and it does not make the character’s belief true.

Refuse to guess when the chosen character has no memory collection.

Another test picks a character that has no memory collection. Enaction writes no memory at all, even though another character’s collection was there to receive it.

For Guide, that means the blue-folder line is not handed to Archivist or to you just to produce a result.

Check your own record after a scene.

One more test takes fingerprints of your profile and your memories before a manual scene. It closes the scene with requests sent straight to the app, accepts one proposed change and rejects the other two. Afterward, both fingerprints match their starting values. Nothing new was added to your memories or your state records, and the character’s collection did get its memories.

A companion test shows the check can fail: adding one memory to your collection changes its fingerprint.

Choosing who speaks, accepting a turn and reviewing what a scene proposes to change are separate decisions.

Explicit rules add useful friction.

Save the character with the turn.

Choice
The chosen character is saved with the turn and its request ID. The workspace locks the role controls while a turn is being prepared or is waiting, and says why (seen in the source and its component tests).
Benefit
The character shown on screen can’t drift away from the character the waiting turn will use.
Tradeoff
To switch characters, you finish or abandon the waiting turn first.

Leave a gap rather than assign an experience to the wrong person.

Choice
If the chosen character has no memory collection, nothing is written, and no one else’s collection stands in.
Benefit
Memories stay with the character they belong to, even when that means recording nothing.
Tradeoff
Someone has to notice the missing collection. Enaction does not repair it.

What went into this work.

Direction
I want to be able to see which character spoke, what it remembers and what a scene proposes to change, so a character’s experience can’t quietly rewrite the person playing it or become settled fact in the story.
What I did
I decide what each project is for and check what comes back.
What the AI did
AI tools write the code, including the twelve tests on this page. An AI review in August 2026 found the problem described at the top of this page, and nine of the tests came with its fix.

How I work with AI tools

What the twelve tests checked.

Twelve tests passed on 19 September 2026 with no failures and no skips. Nine of them came with the fix for the problem the AI review found.

  • With either character chosen, every memory from the accepted turn goes to that character’s collection, and none goes to the other character’s collection or yours.
  • The chosen character is saved with the prepared turn. Sending the same request again returns the original turn, and the same request ID with a different character is refused as a conflict.
  • Enaction refuses your own identity, or a character outside the scene, as the speaker, and writes nothing for a chosen character that has no memory collection.
  • With no character chosen, memories still go to a character, by Enaction’s default order of preference, and never to you.
  • Your profile and memory fingerprints match before and after the tested scene. Two controls show the check can fail: adding a memory to your collection changes that fingerprint, and a different profile name gives a different profile fingerprint.

What is real here

On 19 September 2026, the tests ran Enaction’s own code for preparing a turn, filing memory and reviewing proposed changes, on throwaway databases. Web requests went to the app inside the test process, under the app’s own single-user identity, and no live service was involved.

The role lock is not one of the twelve tests, and this run did not click through it in a browser. The scene-closing test sent its requests straight to the app; when the interface was checked, it had no screen for reviewing a closed scene.

Test scope: isolated SQLite and in-process API checks with a fixed identity. Production operation, the full browser workflow, memory quality and long-story relationship behavior remain unverified.
