Enaction · Role-play memory

A character you play shouldn't rewrite you.

In Enaction you run story scenes and pick which character is speaking. Each character keeps its own memories. I wanted that pick to decide whose memory a turn changes, and never to change yours.

The problem

Picking a character used to change only a label.

With two characters in a scene, one character's line could be filed as the other's memory. An AI review found it in August 2026.

How it works

Whose memory is it?

Imagine a short scene with two characters, Guide and Archivist. Each one keeps its memories in its own collection, apart from yours. The scene is made up to explain what the tests check, so clicking through these steps doesn't run Enaction.

Step 1 of 5

Choose who is speaking.

You pick Guide and type "I will bring the blue folder." That choice says who is talking in this scene. Your own profile stays as it was.

Enaction checks the pick before using it. It refuses your own identity as a character, and it refuses a character who isn't in the scene.

When a turn is prepared, Enaction saves the chosen character with the line. Each request carries an ID so Enaction can recognize a retry. If a retry with the same ID names Archivist instead, Enaction treats it as a conflict and keeps Guide.

Refuse to guess when the character has nowhere to keep it.

Another test picks a character that has no memory collection. Enaction writes no memory at all, even though another character's collection was there to take it.

For Guide, that means the blue-folder line isn't handed to Archivist or to you just to produce a result.

Check your own record after a scene.

One more test takes fingerprints of your profile and your memories before a manual scene. A fingerprint is a code computed from the exact data, so any change gives a different code. The test closes the scene with requests sent straight to the app, accepts one proposed change and rejects the other two.

Afterward both fingerprints match their starting values. Nothing new was added to your memories or your state records, and the character's collection did get its memories.

Two companion tests show the check can fail: adding one memory to your collection changes its fingerprint, and a different profile name gives a different profile fingerprint.

Design tradeoffs

Explicit rules add useful friction.

Save the character with the turn.

The chosen character is saved with the turn and its request ID. While a turn is being prepared or is waiting, the workspace locks the role controls and says why. The character on screen can't drift away from the one the waiting turn will use.

The cost: to switch characters, you finish or abandon the waiting turn first.

Leave a gap before filing a memory with the wrong character.

If the chosen character has no memory collection, nothing is written, and no one else's collection stands in. Memories stay with the character they belong to, even when that means recording nothing.

The cost: someone has to notice the missing collection. Enaction doesn't repair it.

How they ran

On September 19, 2026, the tests ran Enaction's own code for preparing a turn, filing memory and reviewing proposed changes. Storage was in memory or in temporary SQLite databases (small single-file databases). Web requests went to the app inside the test process, under the app's one fixed single-user identity. No AI model, live service, browser or PostgreSQL database was involved.

Limits

  • The scene on this page is made up to explain the tests. It isn't a captured run of the product.
  • A memory filed in the right place still waits for review. Filing it doesn't approve it or make the character's belief true.
  • When the interface was checked, it had no screen for reviewing a closed scene, so the scene-closing test sent its requests straight to the app.
  • The role lock, and the way content waiting for acceptance is shown apart from accepted history, come from reading the source and its existing component tests. Neither is one of the twelve tests, and this run didn't click through them in a browser.
  • Tests on SQLite with a fixed identity don't show how a PostgreSQL database behaves under contention or how real sign-in works.
  • Private source, internal links, personal profiles, memory exports and private story material are left out.
