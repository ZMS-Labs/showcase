Enaction · Roles, interaction and memory

A fictional role should not rewrite the operator.

An operator may speak as a fictional character without making that character’s words part of their own record. Enaction makes the chosen role explicit, carries it through a staged turn, and uses it when deciding whose memory may receive the interaction.

Whose experience is this?

Imagine an operator rehearsing a harmless scene with two fictional participants, Guide and Archivist. The Guide and Archivist scene is newly written for this page to illustrate what the tests check; it is not a recorded session, and these controls do not run the engine. The editable diagrams are not application screenshots, and they do not replay the fictional inputs.

Step 1 of 5

Choose who is speaking.

The operator selects Guide and writes, “I will bring the blue folder.” The choice identifies a participant in this scene. It does not replace the operator’s own profile.

The implementation validates the selection: the real-operator binding and a participant outside the scene are refused as assumed roles.

Keep the staged role stable.

Staging records the chosen role with the input. Reusing the same action key (the request’s unique retry identifier) with a different role is a conflicting request; it cannot silently replace the original.

The existing workspace also locks role controls while staging is in flight or a turn is pending, and explains why.

Attribute memory to the chosen character.

After an explicitly committed manual turn, derivation follows the staged role. In the two-character test, events belong only to the selected character’s collection. The test repeats with each character selected.

Derived memory starts pending. Putting an event in the right collection does not itself approve the event or establish that a character’s belief is true.

A missing target is not permission to guess.

A separate negative case selects a character with no memory collection. Derivation writes nowhere, even though another collection could receive the content.

For Guide, that means the blue-folder line is not reassigned to Archivist or the operator just to produce a result.

Check the operator’s record after the scene.

Another test snapshots the operator’s profile identity and memory event set before a manual scene. It closes the scene through the API, accepts a story proposal, and rejects mind and world proposals.

After processing, both operator hashes match their starting values. No operator memory events or participant-state rows were added. Character memory events exist in the character’s collection.

Selection, accepted history and reviewed effects are separate decisions. The final API check does not demonstrate a change to another product’s canon.

Inspect the assertion summaryWhat the checks establish

Explicit boundaries add useful friction.

Bind the role when the turn is staged.

Choice
Carry role selection into the stored turn and its retry identity, with a visible pending-state lock in the workspace.
Benefit
The displayed role cannot casually diverge from the role the pending turn will use.
Tradeoff
Changing roles is a new decision, not a cosmetic toggle midway through a pending turn. The operator has to finish or abandon that attempt first.

Leave a gap rather than assign an experience to the wrong person.

Choice
A selected character without a memory collection receives no derived events; another participant is not used as a substitute.
Benefit
The system preserves the attribution boundary even when that means producing less state.
Tradeoff
The absence needs attention. This rule does not repair missing collections or prove that every useful memory has been retained.

Direction and work shown.

Project direction
A personally directed, AI-assisted project exploring interaction in which roles, remembered experience and proposed consequences remain inspectable. The goal is to let fictional participants develop without silently rewriting the operator or treating a participant’s beliefs as world truth.
Evidence here
Existing implementation and tests support this narrower role-attribution boundary. The case study does not establish sole personal authorship of code or tests, professional deployment, or a completed interaction product.

Within the creative suite, Neuraxic concerns author-owned canon and branch visibility. Enaction concerns who is speaking and what an interaction may change. Poiesis concerns generation requests and artifact delivery; no live integration with it is demonstrated here.

Twelve checks of a specific boundary.

Twelve existing Python tests passed on 19 September 2026. Zero failures. Zero skips.

The selection ran real staging, derivation and review code against in-memory or isolated temporary SQLite databases. HTTP assertions used an in-process FastAPI test client and a fixed-identity test double. No model or live-service integration was exercised.

  • Attribution: selecting either character directs events to that character’s collection.
  • Request identity: the role is persisted; an identical retry returns the original staged row, while a changed role conflicts.
  • Invalid targets: the operator binding and a role outside the scene are refused; a chosen role without a collection derives nowhere.
  • Operator protection: profile and memory-event-set hashes stay equal in the tested manual scene. Positive controls show the hash checks detect changes to the profile or event set.

What remains unproved

These tests do not establish production authentication, PostgreSQL concurrency, deployment readiness, model quality, long-term relationship fidelity or a complete browser workflow. The role-control lock is shown here as an inspected implementation behavior with existing component tests, not as a browser interaction verified by this Python run.

The scene-close and selective-review check uses APIs; the inspected UI has no scene-close review screen. Private application source, personal profiles, memory exports and story material are excluded. The public diagrams use wholly new illustrative content, not captured application output.
