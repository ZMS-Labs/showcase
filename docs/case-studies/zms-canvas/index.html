Keep the work
when a save fails.

I wanted the work on a canvas to survive a failed save or a conflicting revision. My focus in this PenEcho fork is notebook continuity: keeping pending edits until the server acknowledges them and preserving a separate copy when versions conflict.

Follow the acknowledgment boundary.

A guide to selected assertions in the existing tests. Client behavior uses synthetic payloads and controlled adapters; the storage tests exercise the actual SQLite store in temporary state.

01 · Preserve before sending.

The controller records the full pending canvas payload in its recovery adapter before making the save request. The test checks that the payload already exists when the API adapter receives it.

Write recovery → send → acknowledge → clear

The observed call order is recovery:put, api:create, then recovery:clear. The API stub acknowledges immediately in this test.

02 · Keep an unsuccessful save recoverable.

A controlled API failure rejects the flush. The full payload remains in the recovery adapter and the status changes from “Saving…” to “Save failed”.

Failure is visible; payload retained

This assertion covers controller behavior with a fake recovery adapter. It does not prove browser storage will survive every crash or storage failure.

03 · Do not overwrite a newer revision.

The conflict test starts from revision 4. Its API adapter rejects the update with a 409 response reporting revision 5. The controller creates a new notebook containing the complete pending payload.

Existing notebookr5 reported
Conflict copyr1 created

The test verifies a distinct copy, an unchanged original input record and the “Conflict copy saved” status. It does not perform a live multi-user editing session.

04 · A failed copy is still a failed save.

If the conflict-copy request also fails, the controller rejects the flush and keeps its recovery record. Starting a fallback does not itself establish successful preservation on the server.

No acknowledgment, no cleanup

The complete payload remains pending. The successful and failed copy branches are separate tests, not a recorded sequence from one user session.

05 · Keep the database revision atomic.

The storage tests reject stale and cross-owner writes. A separate malformed tile payload deliberately fails a save, and the current revision stays at 1. A subsequent valid save advances it to 2.

Failed transaction → unchanged revision

Actual temporary SQLite state is inspected. The owner checks establish the store’s boundary, not the identity or security of a production authentication service.

Preserve both versions before resolving the difference.

A conflict copy keeps the choice available.

Constraint
A stale client may hold useful edits even though the server already has a newer revision.
Choice
Retain the complete pending payload and create a distinct notebook when the server rejects a stale update.
Tradeoff
The user may need to compare and reconcile two copies. The controller does not attempt to infer which overlapping canvas changes should win.
Evidence
The tests check both successful conflict-copy creation and failure of that fallback, plus the underlying store’s revision checks.

This is a tradeoff in the fork’s implementation, built on the upstream product and developed with AI assistance.

Reproduce a focused result.

Six existing tests passed on 19 September 2026 against public source revision 986624a, using Node 24.13.0. Zero failures and zero skips. They ran without a model, external service or real notebook data.

In a checkout of that revision, this selection exercises the demonstrated behavior:

node --disable-warning=ExperimentalWarning --test --test-name-pattern "writes complete recovery state before sending|retains recovery state and reports failure|turns a stale update into a complete conflict-copy|retains recovery state when creating the conflict copy fails|saves complete immutable revisions and rejects|rolls back a failed save without advancing" test/notebook-client.test.js test/notebook-store.test.js

The diagrams explain test assertions. They do not show the product UI, validate AI output, demonstrate deployment, or establish complete browser crash recovery. The source remains available under its own AGPL license and notices; no application code is copied into this portfolio.
